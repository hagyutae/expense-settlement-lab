# 경비 정산 시스템 요구사항

경비 청구 파일을 읽어 사내 경비 규정에 따라 검증하고 결과를 표로 출력합니다.

입력 형식과 도메인 모델의 속성은 [`데이터-스키마.md`](데이터-스키마.md), 검증할 규정은 [`경비규정.md`](경비규정.md) 를 따릅니다.

## 처리 흐름

세 단계로 나눕니다. 단계마다 책임이 하나씩입니다.

```mermaid
flowchart LR
    F(["경비 청구 파일"]) --> L["Loader<br/><b>입력</b>"]
    L -- "Expense 목록" --> S["SettlementService<br/><b>처리</b>"]
    S -- "SettlementResult" --> R["Reporter<br/><b>출력</b>"]
    R --> O(["사람이 읽을 문자열"])
```

각 단계는 앞 단계의 결과만 입력으로 받습니다. `SettlementService` 는 청구 목록이 어떤 파일에서 왔는지 알지 못하고, `Reporter` 는 판정이 어떤 규칙에서 나왔는지 알지 못합니다.

이 경계 덕분에 양 끝은 갈아 끼우고 가운데는 그대로 둘 수 있습니다. 입력 형식이 늘어나면 `Loader` 구현체를, 출력 형태가 늘어나면 `Reporter` 구현체를 하나씩 더 만듭니다.

## 프로젝트 구조

```
src/
├── core/
│   ├── domain/          엔티티와 규칙
│   └── service/
│       ├── usecase/     규칙을 적용해 판정
│       ├── input/       파일을 청구 목록으로
│       └── output/      결과를 텍스트로
└── application/
    ├── container.py     구현체를 골라 조립
    └── cli/             인자 파싱과 실행
```

`core` 는 실행 방식(CLI, Web)과 무관한 알맹이입니다. 누가 부르든 똑같이 동작합니다. `application` 은 그것을 실행 가능한 프로그램으로 만드는 껍데기입니다.

폴더마다 `base.py` 에 추상 클래스를 두고 구현을 옆에 둡니다.

## 도메인 모델

`core/domain/models.py` 에 **클래스 이름만 있고 속성은 비어 있습니다.** 이름과 속성 모두 계약이므로 바꾸지 않습니다.

| 모델 | 담는 것 |
|---|---|
| `Expense` | 청구 한 건 |
| `Violation` | 규칙 하나가 잡아낸 위반 |
| `Judgement` | 청구 한 건의 판정 |
| `SettlementResult` | 정산 한 번의 결과 전체 |

**속성 이름과 타입은 [`데이터-스키마.md`](데이터-스키마.md) 에 있습니다.** 그 문서를 보고 채우세요.

## 규칙

규칙 하나는 파일 하나입니다. 판정 방식에 따라 두 종류로 나뉩니다.

| 종류 | 판정 단위 | 받는 것 | 돌려주는 것 |
|---|---|---|---|
| 단건 규칙 | 청구 한 건 | `Expense` 하나 | 위반이면 `Violation`, 아니면 없음 |
| 다건 규칙 | 청구 전체 | `Expense` 목록 | 위반이 걸린 항목의 위치와 `Violation` |

다건 규칙이 따로 있는 이유는 다른 행의 값을 알아야 판정되는 규칙이 있기 때문입니다. 같은 영수증번호가 두 번 쓰였는지는 그 행만 봐서는 알 수 없습니다.

규칙은 **자기 코드와 이름을 갖습니다.** `경비규정.md` 의 항목 제목이 그대로 들어갑니다. `### R001 · 필수 항목 누락` 이면 코드는 `R001`, 이름은 `필수 항목 누락` 입니다. 위반을 만들 때 이 둘을 `Violation` 에 함께 넣습니다.

## 조립

`application/container.py` 가 구현체를 골라 끼웁니다. 추상 클래스와 구현체가 만나는 유일한 지점입니다.

**규칙은 명시적으로 나열해 등록합니다. 모듈을 스캔해 자동으로 모으지 않습니다.**

등록 지점은 두 곳입니다. 애플리케이션은 `application/container.py`, 테스트는 `tests/container.py` 입니다. 조립하는 대상이 서로 다르기 때문에 나뉩니다.

## 출력

`Reporter` 는 **문자열을 돌려주기만 합니다.** 화면에 쓰거나 파일로 저장하지 않습니다. 돌려주기만 해야 테스트할 수 있습니다.

요약에 쓰는 규칙 이름은 `Violation` 에서 읽습니다. 코드와 이름의 대응표를 이 계층에 두지 않습니다.

## CLI

```powershell
uv run settle samples\연구소.csv
uv run settle samples\연구소.csv --in csv --out console
```

| 옵션 | 값 | 생략하면 |
|---|---|---|
| `--in` | `csv` | 확장자로 판단합니다 |
| `--out` | `console` | `console` |

값이 하나씩뿐이지만 옵션을 두는 이유는 형식이 늘어날 자리를 만들어 두기 위해서입니다. 구현체를 고르는 일은 `container` 가 맡고, CLI는 어떤 형식이 있는지 알지 못합니다.

출력은 두 부분입니다. **건별 표**에 청구ID, 성명, 사용일자, 계정과목, 금액, 판정, 위반 규칙 코드가 들어가고, **요약**에 전체·통과·반려 건수와 규칙별 위반 건수가 들어갑니다.

파일을 읽지 못하면 오류 메시지를 출력하고 종료 코드 1로 끝냅니다. 반려 건이 있는 것은 오류가 아니므로 종료 코드는 0입니다.

## 테스트가 기대하는 계약

테스트는 파일을 읽고, 서비스에 넘기고, 나온 결과만 확인합니다. **비즈니스 로직만 검증하므로 `application/container.py` 는 테스트 대상이 아닙니다.**

조립이 필요하면 `tests/container.py` 를 따로 둡니다. 애플리케이션 컨테이너는 로더와 리포터까지 끼우지만 테스트에는 그것이 필요 없고, 테스트가 진입점 조립에 얹히면 CLI나 웹이 바뀔 때 테스트가 함께 흔들립니다.

**클래스와 메서드 이름은 `src/` 골격에 이미 있습니다. 아래는 그 위에 테스트가 추가로 기대하는 것입니다.** 내부 구조는 자유입니다.

| 계약 | 내용 |
|---|---|
| `tests/container.py` 의 `all_rules()` | 구현한 규칙 전체. 규칙을 추가하면 여기에 등록합니다 |
| `tests/container.py` 의 `build_service(rules=None)` | 조립된 서비스. 규칙을 주면 그것만, 주지 않으면 `all_rules()` 로 조립합니다 |
| `CsvLoader().load(경로)` | `Expense` 목록. **파일의 행 순서를 유지합니다** |
| `service.settle(청구목록)` | `SettlementResult`. **입력 순서를 유지합니다** |
| `result.judgements` | `Judgement` 목록 |
| `Judgement.violations`, `Violation.code` | 위반 목록과 `R001` 형식의 규칙 코드 |
| `Judgement.expense.claim_id` | 청구ID. 골든 테스트가 이 값으로 대조합니다 |

규칙별 테스트는 그 규칙 하나만 넣고 돌립니다. 픽스처에 다른 규칙 위반이 섞여도 흔들리지 않고, 실패하면 원인이 그 규칙으로 좁혀집니다.

```python
def test_r001():
    expenses = CsvLoader().load("tests/rules/fixtures/r001.csv")
    result = build_service([R001()]).settle(expenses)
    codes = [[v.code for v in j.violations] for j in result.judgements]
    assert codes == [["R001"], ["R001"], [], []]
```

## 정해지지 않은 것

이 문서는 **무엇을 만들지**만 정합니다. 어떤 라이브러리를 쓸지, 추상을 어떻게 표현할지, 계층 사이에 무엇을 import 해도 되는지 같은 **작업 규칙은 정해져 있지 않습니다.**

정하지 않은 채로 만들면 사람마다 다른 코드가 나오고, 같은 설명을 세션마다 다시 해야 합니다. 그래서 프로젝트 규칙을 `CLAUDE.md` 에 모읍니다. 무엇을 담을지는 챕터 4에서 다룹니다.
